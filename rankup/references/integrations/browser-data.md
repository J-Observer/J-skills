# 集成 · 登录态后台批量取数与网页版 AI Chatbot 取答

> 本文件从 [`integrations.md`](../integrations.md) 拆出（2026-09-30）。路由表、三方服务优先与分析平台接入仍在主文件；浏览器驱动、会话与取数机制归 `opencli` Skill。

## 登录态后台批量取数

### 行级数据的去重键必须能区分同名行

按「主键」去重会静默压掉重复行。实测：一张 104 行的排名表按关键词去重后只剩 67 行——
同一个关键词可以合法地出现在多个落地页上，其中一个词一个人就占了 7 行。
**去重键要带上能区分同名行的字段**（这里是落地页 + 排名），
否则丢掉三分之一的数据而结果看起来完全正常。

判据：去重前后的行数差如果超过一成，先确认这些「重复」是不是真重复，再决定去重键。

### 分页不一定是 URL 驱动的

本文档此前写「分页多半是 URL 驱动，确认之后可以直接拼 URL」。**存在反例**：
某报表 `&page=2` / `&pageNumber=2` / `&offset=100` 三种写法都试过，
页码指示器纹丝不动停在第 1 页，只能点「下一页」并等页码真的变了再解析。
**先拼 URL 试一次，页码没动就老实点按钮**，不要因为「分页通常是 URL 驱动」就假定成功。

### 每页有上限，超出部分不会有任何提示

表格报表常见每页 100 行，第 101 行起**静默消失**——解析结果就是 100 行，
看起来像一个完整答案。实测一个 104 词的域名被截成 100 而全程无报错。
**要么把页翻完，要么把丢掉的量显式报出来**，两者必居其一。
这是本 Skill「不许静默设上限」那条规则在取数场景的具体形态。

适用于「没有 API / API 收费 / 导出扣点数」的场景：SEO 工具、广告后台、分析平台的表格。
细节能力交给 `backlink` 的 [`references/harvest.md`](../../../backlink/references/harvest.md)，本节只记跨工具通用、且已验证的约束。

落盘要求见 [`SKILL.md`](../../SKILL.md) 的「导出物落盘 SOP（强制）」，那是硬性前置条件。

### 接入策略：有 HTTP 就走 HTTP，没有才用 MCP

站主定的默认（2026-08-16）。判据不是喜好，是故障面：

1. **同数据、同额度时，HTTP 严格优于 MCP。** MCP 只是在你和接口之间多加一层
   连接和一个进程，出问题时还要先分辨是接口挂了还是连接挂了。实测 KD 的
   `/kd/mcp` 端点 `Failed to connect (ECONNRESET)` 的同一时刻，HTTP 一次就通。
2. **发现 MCP 入口，先当作「这家有 API」的线索**，回头去找它的 HTTP 文档；
   多数提供 MCP 的服务同时提供 HTTP，KD 就是。
3. **但不要为了原则砍能力。** 付费数据源（Ahrefs、Semrush 之类）的 MCP 往往
   *就是*你被授权的唯一通道，没有可直连的 HTTP 端点——这类继续用 MCP，
   不要为了「统一走 HTTP」把它们摘掉。
4. 摘掉一个 MCP 之前，先确认替代路径**跑通过一次**，不是「文档说有」。

### 动手抓之前，先找官方 HTTP API

第三方工具站的第一步永远是查它有没有官方接口，而不是打开浏览器点。判据很简单：
页面导航里有没有「API」「文档」「MCP」入口，或者试 `/<工具>/docs`、`/docs`、`/api`。
**找到 MCP 入口只当「这家有 API」的线索，落地一律用 HTTP**：同一份数据、同一份额度时，
MCP 只是多一层连接和多一个故障点（实测 KD 的 MCP 端点 ECONNRESET，而同一时刻 HTTP 正常）。

代价是不对称的。有官方接口时，浏览器自动化那条路要多花一个数量级的时间，
还会做出一个**页面一改版就坏**的脆弱脚本；而官方接口通常自带鉴权、配额与缓存说明，
这些信息靠抓包永远推不全。已验证的反面案例：一个工具集合站里只有其中一个工具有公开
API + MCP，其余全靠网页交互——**先查这一步，就能省掉对那一个工具的全部逆向工作**。

同一站点内**不要把一个工具的接口形态外推到其他工具**。同上例，公开 API 走
`/<工具>/api/v1/<工具>`，而其余工具的内部接口走 `/<工具>/api/<动作>`，按前者去猜后者全是 404。

### 看着像埋点的请求头，可能是硬性门槛——用 curl 重放来定性

浏览器里请求成功，不代表那些请求头可以省。会话 cookie、`Referer`、以及形如
`X-<TOOL>-Token` 的自定义头，浏览器都会自动带上，所以**在浏览器里永远看不出哪个是必需的**。

**唯一可靠的判定是脱离浏览器重放一次**：把请求原样搬进 `curl`，逐个删请求头看什么时候开始报错。
已验证的踩坑：某站的自定义令牌头一度被判成「统计用途、非强制」，因为访客不登录也能在页面上用；
`curl` 重放后才发现服务端真在校验——不带或伪造即 403，带上从自己会话里复制的真实值则放行。
**这个误判会让脚本在写完之后才失败，而那时已经没人记得当初为什么认为它可选。**

顺带一条判据：探测端点时 **403 和 404 的区别是有信息量的**。整段路径前缀统一返回 403
通常是网关或鉴权层拦截，说明那不是真实端点列表，继续枚举动作名是浪费；404 才说明路径本身不存在。

### 令牌只能由用户自己提供，不得逆向生成

脚本需要的令牌一律从环境变量读，并在缺失时**明确报错并说明去哪里自取**。

三条红线：不代替用户登录、不代替用户注册、**不逆向令牌的生成算法**。
最后一条尤其要认清性质——推导出签名算法等于绕过访问控制，
无论技术上多容易、也无论站点是否免费，都不做。正确做法是把「需要用户从自己的会话里复制」
这个事实写进脚本的报错信息和文档，让下一个人少试一遍。

### 采集前先把盘面压小，不要先抓再筛

多数这类后台的**筛选器由 URL 参数驱动**：先在界面上点一次，然后读 `location.hash`
或 query string，就能拿到参数名，之后整个筛选过程可以纯脚本化，不必再点 UI。

**先探针，后抓取，这一步不能跳。** 探针只切一遍 URL、只读「共 N 条」这类计数文案，
不抓表格，比正式抓取便宜一个数量级。跳过它的代价是实打实的：对一个结果为空的切片，
带重试的采集循环会白跑满三轮才报失败，几十秒就这么没了；而探针一眼就能看出该跳过。

探针本身要写得轻。**不要在探针里对整个文档跑 `querySelectorAll('div,span,button')`
再逐个读 `textContent`** —— 在大型 SPA 上这一句就足以让渲染进程卡死，
后续所有调用一起超时，只能重载页面从头再来。要读的如果只是页面顶部一小块文案，
直接对那块区域截图去认，比在页面里跑重查询更省也更稳。

### 短种子词会被子串匹配污染，抓完必须验一遍相关性

「语句匹配」这类筛选**未必是词级匹配，很可能是子串匹配**。
后果是：种子里含常见字母序列时，会大量命中毫不相干的词
（实测一个两字母的种子词命中了一大批把该序列夹在单词中间的长尾词，
八十多个结果里只有一个是真正相关的）。

因此**每个新种子抓完后必须先验相关性再进分析**：对结果做一次关键词包含检查，
相关率过低就判定「种子选错」，不要把它的数字并进汇总表 —— 这类污染在汇总层面
表现为「体量很大、难度很低」，看起来恰恰像最好的机会。

同样地，**种子词与它所在的品类未必对得上**。若某个品类的流量其实挂在具体实体名下
（型号、作品名、产品名），用品类词当种子就什么也捞不到。判据是短语匹配结果数极少
而相关词数量巨大 —— 说明需求真实存在，只是不长在这个词上。

### 表格通常有每页硬上限，用参数分档代替翻页

虚拟滚动表格常见每页 100 行上限，翻页控件还要滚到底才进 DOM。
**把某个数值维度切成一串窄区间，每档独立抓第一页**，比驱动翻页稳定得多，也更容易断点续抓。
分档时用探针确认每档不超过上限，否则会静默截断。

### 后台标签会让采集假死，这是最常见的失败原因

浏览器对非可见标签同时施加两种限制，症状不同、要分别处理：

- **定时器节流**：`setTimeout` 实测被拉长到数倍，长循环从几秒变成几分钟。
  可以在页面里起一个**极低音量的持续音频源**来豁免深度节流；但音频上下文需要用户手势才能
  `running`，只在页面里创建而不激活是无效的 —— 必须验证它的 `state`，不要假设生效。
- **SPA 不挂载**：很多前端框架在 `document.hidden` 时不渲染虚拟表格，于是导航之后抓到 0 行。
  伪造 `document.hidden` / `visibilityState` 有时可行，但不保证 —— 最可靠的做法仍是
  **每隔十几秒对该标签做一次极小区域的截图**，代价远低于整屏截图，且能真正把标签前台化。

判据：`scrollTop` 几乎不动、进度日志长时间不增长，就是被节流了。
**此时不要重发采集任务** —— 旧任务还在跑，两个循环叠加会产生互相覆盖的重复文件。

### 采集与解析的通用工程约束

- **CDP 超时不等于任务失败**。长循环一律「触发后立即返回」，再用单独调用轮询进度，
  不要 `await` 整个循环。超时后回查进度，常发现活儿早干完了。
- **虚拟渲染会漏单元格**，同一行在不同滚动位置的字段数可能不同。
  解析**必须按模式识别每个 token**（是体量？是百分比？是货币？是域名？），
  绝不按列序取值 —— 按位置取列必然把数字当成名称。同一条记录保留字段最全的那份。
- **不同报表的列位不同**，即使在同一个后台里。换一张报表就要换一个 parser，复用会全线错位。
- **结果集很小时反而会失败**，而且是三处一起失败，大表全都恰好绕过：
  ① 小表不产生滚动容器，「找最大可滚动元素」的定位法落空；
  ② 内容全部落在页面顶部，被「忽略视口上方 N 像素」的阈值滤掉；
  ③ 扫描范围若绑在①找到的容器上，①一旦落空或选错元素，就一行也扫不到。
  修法：定位不到滚动容器要回退到文档根；纵向阈值只用于挡住页面顶栏，不要设得太高；
  **扫描范围直接用整个文档**，靠横向坐标下限排除左侧导航即可。
  实测全文档遍历只需毫秒级，「限定容器是为了性能」这个前提通常不成立。
- **因此采集器必须用最小结果集验收。** 只用大表测过的采集器等于没测过 ——
  上面三个缺陷在有上百行数据时全都不会暴露。
- **左侧导航等页面装饰会混进行**，按横向坐标下限排除内容区之外的元素。
- **语言/噪音过滤只标记，不静默删除**。过滤正则必然有误杀（常见停用词会撞上目标语言的正常词），
  把判断结果作为一列写进产物，让人来裁决，不要在采集阶段就丢掉行。

### 滚动扫描必须设上限，心跳必须真的能前台化

两个会让长循环**静默挂死**的细节：

- **滚动上限**：`for (y = 0; y <= sc.scrollHeight; y += step)` 在滚动容器选错时会失控 ——
  某些容器的 `scrollHeight` 极大，循环永远跑不完，整个任务停在那一项不再前进，
  外部看起来像是「卡住了」而不是「出错了」。一律加一个绝对上限。
- **心跳要选对动作**：单纯「等待」不会让后台标签前台化，节流照旧；
  **截图类动作才会**。抓取期间的心跳必须用截图（取最小区域，代价比整屏低一个数量级），
  否则会误判成任务死了而去重发，反而引发并发循环。

### 同一时间只允许一个采集循环

长循环靠改 URL 驱动页面，**两个循环并发就是两只手抢同一个方向盘**：
它们互相打断导航、日志被后启动的那个清空、同一目标被抓两次且内容不同。

因此：

- **看到「还没结束」时不要重发任务。** 旧循环通常只是被节流拖慢了，不是死了。
- 确实要换任务时，**重新加载页面**是唯一可靠的终止方式 ——
  在页面里设一个「已完成」标志并不会停下已经在跑的异步循环。
- **接收端/落盘端必须假设同一切片会被重复提交**，且两次内容可能不同。
  规则是**保留数据行更多的那份**，绝不能盲目后写覆盖 ——
  谁最后到达纯属偶然，覆盖会静默丢掉更完整的那份。

### 判断纪律

脚本负责**采集**，不负责**裁决**。以下必须由人或 agent 判断，不能自动出结论：
过滤规则会不会误杀、全局口径里有多少是目标市场、「体量大」是否等于「该做」。

## 网页版 AI Chatbot 取答

有些能力只以**聊天网页**的形式存在：要登录态、按条扣积分、没有 API 或 API 另收费。
驱动脚本见 `<rankup-skill-dir>/scripts/chatbot-drive.browser.js`（`probe → init → send → wait → capture → read`）。
选择器 profile、账号与登录态属于项目侧，放 `<project>/.rankup/scripts/`，不进本 Skill。

### 触发语与项目侧登记

用户往往用**工具的俗称**下指令（「和某某 AI 对话一下」「问问那个 SEO Agent」），
不会重述地址和流程。所以每接入一个这类聊天页，都要在项目侧
`<project>/.rankup/scripts/RUNBOOK-<工具>.md` 的开头写一行 **触发语 → 走本 RUNBOOK 全套**，
并在 `.rankup/INDEX.md` 的脚本表登记。以后听到那句俗称，直接照 RUNBOOK 执行，不必重新摸索。

### 取全文用「复制」按钮，不要截图 OCR

回答动辄几千字、带表格与代码块。滚动截图慢且丢字符，而**页面自己的复制按钮吐的是原始
Markdown**，一次点击就是全文。

读剪贴板（`navigator.clipboard.readText`）要权限 + 页面焦点，自动化里两者都不稳。
**改劫持写入侧**：点击前包一层 `clipboard.writeText`，同时监听 `copy` 事件兜住
`execCommand` 老写法。页面照常复制，你拿到同一份文本，全程零权限提示。

### 会话找回：URL 里通常没有会话 id

这类页面常常**不把会话 id 写进 URL**，甚至主动擦掉查询参数
（实测见过 `history.replaceState(null, '', location.pathname)`）。三个后果：
存下来的 URL 只会把你带回空白的「新对话」；刷新后当前会话只能从**侧边栏**点回来；
刷新还会连注入的 helper 一起清掉，**重新加载后必须重新注入再 `init()`**。

所以**开新会话就当场 `session()` 记下 `{id, title}`**，连同问了什么写进项目记忆
（`<project>/.rankup/data/<工具>/conversations.md`）。id 一般挂在侧边栏条目的 `data-id` 上，
是稳定主键；标题是页面从首个问题**截断**生成的，改不了且极易撞车——**认 id，不认标题**。
找回用 `open(id)`，只记得大意时 `open('片段')` 走搜索框（这类搜索通常标题正文一起搜）。

恢复后每条回答的复制按钮都还在，**重新 capture() 取全文不扣费——别为了拿全文重新提问**。
另注意搜索式找回后要**清空搜索框**：非匹配条目常被移出 DOM，不清就会把会话总数误读成 1。

账号多是跨项目共用的，侧边栏里会有别的项目的会话。**台账只登记本项目的那几条**，
别把别的项目名抄进当前仓库。

### 三个必踩的坑

- **CDP `Runtime.evaluate` 约 45s 超时，但可用预算远小于 45s。** 实测 `wait(28000)`
  照样超时——流式输出期间渲染器很忙，调度开销不止那 17s 差额。**轮询单次 ≤20s 且可续跑**；
  未完成就再调一次，代价只是一次往返。超时拿到的是「渲染器无响应」，那次调用的副作用你无从确认。
- **输入框多是受控组件**，直接 `el.value=` 不触发框架状态更新，点发送会被当成空。
  必须用原型链上的原生 setter 再派发 `input` 事件。
- **工具返回值会被截断**，别指望一次读回几千字。`read(from, len)` 按 ~900 字分片读。

### 判断纪律

按条扣费，所以**问题一次问完整**，别靠追问补细节——追问是另一次消费。

它对**你自己站点**的断言必须先核实再采信：这类 Agent 的 on-page 审计常常抓不到
JS 注入的 JSON-LD、把锚点总数报成外链域名数。`curl | grep` 一遍是几秒钟的事，
把错误结论写进项目记忆则会误导后面每一轮。
反过来，它**调外部工具查回来的数据**（KD、SERP 盘面、DR、竞品体验分）可以直接用——
那不是它的判断，是它的检索。

**别为了抬审计分去违反自己的内容红线。** 这类工具的「前 N 词命中率」多是**精确短语计数器**：
把目标短语再塞一次，分数立刻翻倍，可读性和反堆砌纪律却双输。分数是代理指标，不是目标；
改写语序让首屏先回答用户问题是真收益，为凑计数插入第三次同一短语不是。
判据：**这条改动如果没有这个分数，你还会做吗？** 答案是否，就别做。

反过来也别把它当橡皮图章。把你的裁决连同理由一起说给它、明确要求「别迁就我」，
它常能指出理由里站不住的那一层——结论也许不变，但你会知道自己真正的依据是什么。
留在记忆里的应该是**经得起反驳的那个理由**，不是最初随手写下的那个。
