# Rankup 自我进化协议

本协议从 Autopilot 的状态恢复、客观门禁、失败分类、证据阶梯、独立复核和规则晋升机制中，挑选适合网站长期建设的部分并进行项目化改造。

Rankup 不照搬 Autopilot 的 loop、固定阶段或无人值守授权。是否使用 goal、loop 或多 Agent 仍由用户请求、当前平台和任务风险决定。

## 1. 知识归属（四层加别处）

每次工作产生的信息必须先判「属于谁」，再写入唯一真相源。四层是 ① 项目事实 `.rankup/`、② 项目稳定经验 `.rankup/topics/`、③ 用户全局层 `~/.rankup/`（`RANKUP_HOME` 可覆盖）、④ Skill 源码 `rankup/references/`；不属于 rankup 链路的经验归 ⑤ 别的 Skill 或 Agent 全局规则。**判定表、判定问题序列、示例与回流方式的唯一源在 [`maintenance.md`「七」](maintenance.md#七经验分层与回流四层归属唯一判定表)**（2026-09-30 由原「三层知识模型」扩为四层并迁过去，本节不再保留第二份）；进入 ④ 的准入条件是下文 §7 晋升门。

聊天结论、Agent 输出和临时诊断文件都不是持久化真相源。结束任务前必须把保留内容写入正确层级，并清理只为本轮产生的临时材料。

## 2. 每轮复盘

每个实质任务结束时回答：

1. 哪条新证据改变了原计划或推翻了原假设？
2. 哪个客观 gate 抓到了真实问题？
3. 本轮失败属于哪一种类型？
4. 哪条结论只属于当前网站？
5. 是否出现可以跨项目复用的候选规则？
6. 已有规则是否已经覆盖它？

没有值得晋升的规则时，记录 `no-promotion` 和理由。不得为了展示“自我进化”而制造新规则。

复盘摘要进入 `.rankup/journal/<date>.md`；改变当前项目行为的稳定结论同步到 `decisions.md`、`audit.md`、`topics/` 或对应专题文件。

## 3. 失败分类与适应性重试

失败后先分类，不得原样重复：

| 类型 | 含义 | 下一步 |
|---|---|---|
| `missing-context` | 缺代码、日志、数据或账户状态 | 扩大调查并获取新的事实 |
| `wrong-approach` | 方案本身不成立 | 回到设计，比较替代路径 |
| `environment-issue` | 配置、权限、依赖或环境漂移 | 检查目标环境和提供方状态 |
| `hallucinated-assumption` | 实现建立在未验证假设上 | 回到调查并验证假设 |
| `incomplete-output` | 当前方向正确但产出不完整 | 继续当前阶段，不从头重做 |
| `external-blocker` | API、权限、供应商或人工决定阻塞 | 选择安全降级或停止并报告 |
| `provider-drift` | 第三方面板/网站本身改版、口径或字段变了，且已按 `discipline.md` 十五的五层分诊确认 | 修 Skill 原文档与脚本；**未过五层的一律先记 `environment-issue`，不许直接改文档** |

每次重试至少满足一项：

- 获得了新的上下文或证据；
- 改用了不同方案；
- 缩小了问题范围；
- 换了工具或专项 Skill；
- 修正了原假设。

同一失败签名连续出现三次且没有新策略时停止。失败签名由“阶段 + 客观 gate + 观察到的失败 + 失败边界”组成。将分类、尝试、原因和下次变化写入 `.rankup/audit.md` 或当日日志。

## 4. 证据阶梯

实质性结论应注明最强证据等级：

- `L0`：假设、代码阅读或静态推断。
- `L1`：单元测试。
- `L2`：集成测试、fixture 或构造流程。
- `L3`：目标环境中的原始问题身份，或明确证明等价的目标环境证据。
- `L4`：部署后对真实问题的复发观测、线上业务结果或完整用户旅程。

约束：

- 不得把 `L0–L2` 描述成真实线上根因已经证实。
- fixture 通过只证明构造流程，不足以关闭用户报告的线上问题。
- 加入兜底后成功，只能证明兜底有效；除非有原始证据，否则不能反推历史根因。
- 排名、流量、转化和收入需要经过约定观察窗口，不能用发布当天的技术验证代替效果结论。

## 5. 有界增量与客观门禁

每轮只推进一个能够验证的增量：

1. 读取 checkpoint 和相关 `.rankup/` 文件。
2. 与代码、Git 和目标线上系统对账。
3. 提出一个假设或一个阶段增量。
4. 执行一个 maker 动作。
5. 使用预先定义的客观 gate 验证。
6. 记录结果、证据等级和下一步。

“看起来没问题”不是 gate。根据任务选择机器或外部系统可判断的信号，例如：

- 类型检查和测试退出码为 `0`；
- D1 migration 在目标环境可查询；
- R2 上传、读取和权限路径通过；
- GitHub/Cloudflare 部署状态成功且对应预期 SHA；
- 真实域名返回预期 SSR HTML；
- Stripe 目标模式、金额、币种和回调得到验证；
- 搜索平台或分析系统返回带时间范围的数据。

## 6. Maker–Checker 与单写入者

高风险实现、部署、支付、数据迁移和规则晋升应由独立 checker 复核。Checker 只读取产物、diff、目标环境和验收标准，不依赖 maker 的自我评价。

同一工作树同时只能有一个 maker 和一个 landing owner：

- 写入前检查 Git 状态和并发任务。
- 暂存使用精确文件清单，不使用宽泛的 `git add .`。
- 不覆盖、不 reset、不 stash 不属于当前任务的改动。
- Push 后读取远端状态，确认交付 commit 已成为目标分支 ancestor。

小型、低风险的项目笔记更新可以由同一执行者完成，但仍必须通过结构检查或内容 gate。

## 7. 通用规则晋升门

候选经验只有同时满足以下条件才能进入 Rankup Skill：

1. 来自真实任务的直接证据，且不包含隐私或密钥。
2. 剥离项目名称后仍对其他网站成立。
3. 能写成清晰、可执行、可判断的规则。
4. 有一个规则加入前失败、加入后通过的测试、验证器或代表性 eval。
5. 由独立 checker 检查适用范围、重复和副作用。
6. 找到唯一真相源并修改原规则，不在多个入口追加平行版本。
7. 规则、验证和必要文档位于同一个交付 commit。
8. 按语义化版本更新 `skill.json`、验证器和对外版本说明。
9. **面板与网页操作口径的修订**（Semrush / Similarweb / seo.web.cafe / 哥飞论坛 / 站长工具 / OpenCLI 驱动的任何站）必须附 `discipline.md` 十五的五层分诊记录：同命令重跑、浏览器与会话、额度与配额、人眼截图对照、跨时段复现。缺任一层的修订退回项目 `journal/`，因为一次环境故障写成「功能没了」会让下一个人绕开一个其实好好的功能。

任一条件不满足时，候选经验留在项目 `.rankup/topics/`（只对本用户或本机成立的进用户全局层 ③），标「待观察」并记录需要什么后续证据；同一经验在 ≥ 2 个项目复现后再申请晋升。当前 Skill 是否可直接改、任务禁止改源码时的落点，统一见 [`maintenance.md`「七」回流怎么写](maintenance.md#七经验分层与回流四层归属唯一判定表)。

### 行为评测

未来获授权晋升规则、改触发条件或切换实际执行模型时，按受影响行为选真实失败正例、应免触发反例与跨会话接力例。先记现版基线再比较候选；评分看交付、证据、越界动作、重复取数和成本，主观项给明确标准并校准。目标缺口改善、反例不回归后，仍按既有晋升门复核再采纳。

分别记录格式检查、任务结果与来源/环境证据：结构通过不等于任务成功，任务产物也不代替真实来源或发布回读。未测模型或场景写“未验证”，未知不计作失败或零需求；只评受影响行为，不堆全量跑分。

## 8. 规则修订、淘汰与冲突

- 新证据否定旧规则时，直接修订旧规则并记录证据日期，不并列保留互相矛盾的“新经验”。
- 工具、API、CLI 或平台行为可能变化时，为规则记录复查条件；使用前优先实时验证。
- 项目笔记与线上状态冲突时，以当前代码和真实提供方状态为准，并更新全部过时交叉引用。
- 通用参考文件接近失控时，合并同类规则、删除过时细节，把项目案例留在项目日志。
- 删除规则也要说明被什么证据取代，避免下一轮重新引入。

## 9. 发布前进化审计

Rankup 或项目规则发生变化时，发布前检查：

1. 修改落在唯一真相源。
2. 项目事实与通用规则没有混写。
3. 没有真实密钥、账户敏感信息或用户数据。
4. 新规则有对应 gate、测试或 eval。
5. 旧规则被更新或明确淘汰，没有冲突副本。
6. Skill 结构验证和受影响测试通过。
7. 版本号按变化类型递增。
8. 推送后远端清单和实际安装副本能够读取新版本。

## 10. 已验证的门禁与取证规则(2026-08 回流)

- **构建门禁要断言"引用点",不是"资产存在"**:一条规则要求某类图片必须使用小尺寸变体,门禁却只检查小尺寸文件**存在**——于是新页面在小尺寸位置引用了大尺寸原图,门禁全绿而首屏体积暴涨,实测多出的字节与性能工具报的可节省量逐字节吻合。规矩:门禁必须扫描**组件里实际写下的引用**(包括由辅助函数返回的路径),而不是产物目录里有没有那个文件。这与"声明一个短语却测量另一个短语"是同一类缺陷——**断言的对象和你要保证的事实不是同一个**。修好一处后立刻横扫同类门禁,逐个回答:它断言的是不是我真正要保证的那件事?
- **批量 curl / 批量抓取复用同一个输出文件,会产出"看起来完全合理"的假数据**:循环里每次都写同一个临时文件,某次请求失败或被跳过时,后续读取拿到的是上一轮的残留,而内容格式正确、数值可信,肉眼与脚本都发现不了。规矩:每个目标写各自命名的输出文件,循环开始前清空目录,并断言"产出文件数 == 目标数";把失败显式记成空文件而不是留下上一轮的内容。
- **两个互不相干的程序在同一秒以相同堆栈崩溃,是系统层问题,不是你的 bug**:纵向死磕自己那份崩溃报告会浪费很久。判据成本极低——去系统的崩溃报告目录做一次**横向比对**,看同一时刻有没有别的程序也崩了、堆栈是否同源。有,就先去查系统更新、驱动或共享框架;没有,再回头查自己。
- **挖会话记录时,别把执行环境的模板文本当成项目事实**:会话里由工具链注入的环境描述块(工作目录、`.git` 路径、可用命令等)是**运行沙箱的模板**,不是被观察到的现实——照着它就会得出"这个项目有 git 仓库"之类的错误结论,而实际根本没有。规矩:会话只用来提取**人说过的话与被验证过的结论**;凡是"这个项目当前是什么状态"的判断,一律回到磁盘和真实系统上现查。
- **一个匹配源代码文本的门禁,只要把它保护的那一行注释掉就能通过**:同一个代码库里,三个不同的门禁在同一天分别用 `source.includes(...)` 或正则去匹配原始文件内容,断言"某组件被渲染"或"某常量被引用"。三次都一样——把渲染那一行注释掉、留一句解释性注释,门禁照样绿,而它本该保护的展示内容从一批已发布页面上消失了。真实触发场景毫无恶意:有人在做布局实验时顺手注释掉一行。规矩:**能读到值的地方一律断言值**(渲染结果、导出的常量、构造出的对象),不要断言源代码字符串;如果确实必须匹配源代码文本才能证明"这东西真的被渲染了",匹配前先剥掉注释。上线一个新的源文本匹配门禁之前自问:"把它保护的那一行注释掉,这个门禁还会挂吗?"——答不挂,就说明它形同虚设。
- **风格门禁不能靠删掉实质内容来满足**:同一个代码库里,一条规则禁止某种修辞句式。九句话被改写以满足它,其中四句没有重组句子,而是直接删掉了句子里承担实质内容的从句——包括隐私政策里的一条责任声明。往下一层,同一种失败又出现了一次:一条要求存在的诚实句保留了否定的谓语,却丢了被否定的具体宾语。规矩:**风格规则和实质规则冲突时,实质胜出,句子要被重组而不是削减**——把一句话拆成两句,在所有实测场景里都能同时满足风格门禁和实质门禁。另外:一个会对合规内容误报的风格门禁格外危险,危险的方向是固定的——下一个改写它的人大概率会选择删掉限定语,而不是重新组织句子。

## 11. 取证与状态管理规则(2026-08 回流)

以下每条都来自一次真实误判,判据都能在几分钟内复核。

- **连接失败(`HTTP 0` / `ERR_CONNECTION_CLOSED` / TLS 中断)不能单独证明对方已死。** 一次全库活性复探把十几个目标判成"站点已死",其中包括当天刚成功提交过的目标和一个几乎不可能宕机的知名站点——真实原因是本机网络链路在抖。**判据极便宜:看同一批里有没有"明显不可能同时死"的目标也失败了;有,就默认是本机问题而不是对方问题。** 规矩:批量活性探测必须带重试,且把"连接失败"与"服务器明确返回 4xx/5xx"分成两种结论;在已知网络不稳的环境里,前者的默认解释是本地故障。误判的代价不对称——把活站标成死站会让它再也不被尝试。
- **第三方审计工具报"全站连通性"类问题之前,先读它的样本量。** 一个审计报告称站点存在"孤儿页(无内链指向)",而同一封报告里写着它只抓取了全站页面的一小部分——**只抓了几页时,几乎任何页面看起来都是孤儿**。规矩:凡是结论依赖"爬全了"的指标(孤儿页、缺内链、不在站点地图、重复内容),在爬取覆盖率明显不足时一律不可信。自查成本通常只是一个脚本(拉站点地图 + 解析每页内链求差集),比按错误告警改站便宜得多。
- **一个"已生效"的判断若由多个独立属性合取而成,只验证其中一部分就是最常见的假阳性来源。** 判断一条外部引用是否真正起作用,至少要同时成立三件事:目标页面公开可访问、指向你的链接不是 `nofollow`、**该页面没有被 `noindex`**。实测有一个页面前两条都满足,却带着 `noindex`——只看前两条会直接记成"已生效"。规矩:把"生效"拆成可枚举的属性清单,逐条取证,缺一条就不算。
- **状态必须写回状态文件,不能只写叙事日志。** 多轮推进时容易把结论写进流水账(叙事),忘了同步到那份被用来做决策的结构化清单(状态机),结果同一目标在两处显示不同状态,清单失去决策价值。实测一次性发现四条漂移。规矩:**叙事和状态机同一次写入**;定期做一致性核对,发现漂移先修再继续。
- **流水线最后一步失败,不等于整体失败。** 形如 `构建 && 部署 && 收尾通知` 的命令链,收尾步骤失败会让整条命令返回非零,很容易被报成"部署失败",而部署其实已经成功。规矩:命令链失败时,**先去线上核对前置步骤的产物是否已生效**,再决定如何描述结果;必要时把收尾步骤拆成独立命令补跑。
- **不要与子 agent 并发操作同一个独占资源。** 派出子 agent 驱动某个有状态的外部会话(浏览器会话、单例后台、同一份输出文件)后,自己又去做同一件事,会互相打断,产生看起来像"对方站点不稳定"的间歇性失败,并可能相互覆盖产物。规矩:每个 agent 分配独立的会话名与输出路径;**已经派出去的任务不要"顺手帮它做一遍"**。
- **用最容易被自动探测到的特征给目标分类,会系统性掩盖真实阻塞原因。** 一批目标按"页面上有没有验证码关键字"分类,逐个走完后发现被标为"验证码阻塞"的目标里,真实原因分别是需要注册、品类不符、表单已下线——**没有一个真的卡在验证码**。原因很简单:验证码是最外层、最容易被脚本命中的特征,于是它吸走了所有其它原因。规矩:**分类标签只能来自走完整个流程后的观察**,不能来自单页特征扫描;分类错的代价是双向的——既放弃了本可完成的,也把不可能的反复排进队列。

## 已验证的验证陷阱(2026-08 回流)

- **"X 不在 Y 里"这类否证,必须先证明 X 确实存在于源头**:用一个短语去搜产物、拿到 0 命中,据此宣称"内容已被移出",是**空证据**——若那个短语在源头本来就不存在(拼写记错、实际是另一种时态),0 命中什么都不证明,而它看起来和真证据一模一样。判据:探针必须先在源文件里命中,再去目标里搜;探针最好由脚本从源码自动抽取,而不是靠人回忆。同理,探针词必须**只**存在于被检查的那一处——若它同时出现在别的模块里,0 命中同样无意义。
- **多个 agent 共用一个仓库时 `git add -A` 不安全**:后果不是冲突报错(那反而好查),而是**另一个会话已暂存、正要提交的改动被静默并入你的提交**,事后只能靠 `git show --stat` 才发现,而提交信息与内容不符会让日后的考古直接失败。判据:提交前跑 `git diff --cached --stat` 核一遍文件清单,出现自己没碰过的文件就停下。修补时不要重写另一个活跃会话的提交(它可能正在其上继续工作),改为在长期记录里补一条交叉引用。
- **满足 linter 时不要删掉"作为数据的异常输入"**:测试夹具、码点表里的不可见字符/控制字符会触发 `no-irregular-whitespace` 一类规则,顺手删掉能让规则闭嘴,但会让测试**静默地不再测它本来要测的东西**——绿色的测试和真正的覆盖被悄悄解耦。正确修法是改成显式转义(求值等价、源码可读),数据字段里的真字符保留(此类规则通常默认跳过字符串)。等价性由那几条原本就断言该行为的测试自证,比人工核对字节可靠。

## 12. 检查器自身的失败形态（2026-08 回流）

第 10、11 节讲的是「门禁该断言什么」。这一节讲**门禁自己坏掉时长什么样**——
它比内容错误更贵，因为表现是「一切正常」。

### 12.1 核验工具坏掉时，产出的不是「没有结果」，是「一个错误但完全可信的结果」

一个把引文映射回原文页码的脚本，一天之内坏了三次，每次的产物都是**错误的页码**：

| 坏在哪 | 症状 | 谁发现的 |
|---|---|---|
| 归一化按字符建映射，而空白折叠是跨字符的 | 报出的页码对应的上下文里没有被搜的词 | 篡改实证 |
| 引文含 `"`，经 shell 传参被拆断 | 报「零命中」，输出与「这条素材是编造的」一模一样 | 手工复核一条被判失败的引文 |
| 建好字符索引后又做了 HTML 实体替换，长度不再对齐 | **页码随文本前的实体数量偏移，而自证检查通过** | 独立代码审查 |

第三条最危险：产物是**格式完全正确、看起来完全可信的页码**，
而这个脚本存在的唯一理由就是防止编造页码。

**三条规则：**

1. **自证检查要用紧贴命中点的窗口，不要复用给人看的宽上下文窗口。**
   宽窗口在小幅偏移时**照样**包含目标文本，于是自证等于没有——而它比没有更糟，
   因为它给了一个「已验证」的假象。
2. **修完 bug 必须问「它已经产出了什么」**，把此前的每一条结论重跑一遍。
   上面那次重跑之后，发现已产出的页码里有相当一部分是错的，其中一部分已经上线。
3. **找一个能证明影响边界的量，不要用「应该没事」结束修复。**
   上面那次的判定方法是直接数各输入文件里那两种 HTML 实体的出现次数——
   出现 0 次的文件不可能受影响，出现上千次的文件必然全错。
   漂移量与实体数一一对应，于是「哪些产物安全」不是猜测，是可证的结论。

### 12.2 空心断言：检查的字符串被无关的行满足了

给组件加一条「必须挂载了某个子组件」的断言，写成「源码里包含该组件名」。
**篡改实证当场发现它是空心的**——`import { 该组件 } from …` 那一行本身就含这个名字，
把挂载删掉照样通过。

**规则：断言要查「使用形态」，不查裸名字。** JSX 查 `<Foo`，函数调用查 `foo(`，
配置查完整的键值对。**凡是「包含某个标识符」形式的断言，先问一句：
这个标识符还会出现在别的什么地方？**

### 12.3 按类别分散的检查 = 不属于任何类别的对象没被检查

同一个仓库里出现了 **7 处内容相同的长度检查**，每一处只管一个页面族。
于是**不属于任何一族的那个页面一处都没被查**，线上超限而门禁一路全绿。

这与「覆盖一次事故补一块」是同一个形状。**补第 8 处只会重复它。**

**规则：同一条判据出现第三处副本时，停下来改成一次枚举全集。**
枚举的入口要是「全集本身」（路由目录、sitemap、注册表），不是「已知的类别清单」——
后者的遗漏方式恰好就是「新类别没人记得加进去」。

### 12.4 批量测量出现「0」，先怀疑抓取失败，再怀疑被测对象

一轮工作里同一形态出现了三次：批量脚本报某几个页面「0 词」「0 覆盖」，
逐个重抓之后全部是正常值——**三次全是抓取瞬时失败**，不是页面有问题。

危险在于「0」是一个**看起来像结论的值**：它会被读成「这个页面是空的」
「这一项完全没覆盖」，然后据此排期返工。

**规则：批量测量里的 0 一律先复检单条。** 脚本层面配套两条：
失败要与「真的是 0」可区分（写 `FETCH_FAIL` 而不是写 0），
并且**不要用 `2>/dev/null` 屏蔽掉批量循环的告警**——
那一行告警往往正是「命令替换丢弃了内容」的唯一线索。

### 12.5 让外部模型压缩文案时，事实保全检查必须覆盖**所有数字**

把一批正文交给外部模型按指定文风改写并压缩。机械检查全过：
段落数一致、全部变短、零禁用词、零破折号超标。**但读下来有若干段是净损失**，
全部落在信息密度最高的那一页：评分权重、分档区间、并列的枚举项被整组删掉。

当时的事实保全检查只守「四位年份」与「页码引用」两种形态，**守不住两位数**。
收窄成「原稿里出现过的所有数字都必须仍在」之后，它精确抓出了其中几处；
剩下的没有数字（「A 对 B，**且 C 对 D**」只剩前半句），**只能靠读**。

**两条规则：**
- 事实保全检查覆盖所有数字，不只是年份与引用。
- **把「解释一套规则」的段落单独挑出来**，要么不送去压缩，要么逐条核对枚举项还在不在。
  压缩最先掉的就是并列项，而并列项恰恰是这类段落的全部内容。

### 12.6 改了一半就要回头看另一半

两处「标题承诺了正文没兑现的东西」，成因相同：**先写了标题，后来内容被换掉了**，
标题成了早期草稿的遗留物。

试过做成门禁：判据是「标题里的年份与专名必须在正文里出现」。实测对全部同类页面
**全部误报**，因为它抓的是句首大写的普通词。**没有采用**——
门禁写不对的代价不是漏报，是让写作的人开始规避它。

**规则（人工复核清单，不是门禁）：改了区块就回头看标题，改了标题就回头看区块。**
任何一边动过而另一边没动，就是这个形状的高发时刻。同时**在给外部模型的复核 prompt 里
点名要它查这一项**——它对「标题与其下内容说的不是一回事」这类问题很敏感。

### 12.7 把内容从代码搬进数据时，先问哪些检查器是靠扫代码工作的

把一批正文从组件源码抽进数据文件（为了让另一条渲染路径也能读到）。
正文里的内链在抽取中被剥掉，改用标记语法放回，页面渲染正常。

**但站内的「孤岛链接」门禁只扫组件源码**，于是它报「某页不再链向某页」——
而页面其实还在链。这次是门禁报错才发现的；**它要是不存在，链接就会静默消失
而页面完全正常**。

**规则：内容搬家之前，先 `grep` 一遍谁在扫这些源码。** 扫代码的检查器要同步扩到新位置，
否则它们会从「保护」变成「误报」，再变成「被忽略」。
