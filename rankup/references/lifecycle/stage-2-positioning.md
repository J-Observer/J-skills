### 2.1 第一目标是拿到流量，并选定语种

立项的第一个决定不是功能，是**做哪个语种、哪个市场**。市场是全球——任何语种任何国家，
有流量就做。方法走 [`trends.md`](../trends.md) **W1「小语种/小国市场竞争力探测」**：
同一个词根在各语种/地区的量、KD、CPC 并排比较，挑「量大、KD 低、有人花钱」的那个。

**裁定要精确到 locale（语言-地区）**：同一语言分布在多个国家/地区时（西班牙语的墨西哥与西班牙、
葡萄牙语的巴西与葡萄牙……），按 [`playbooks/research/p2-keyword-root.md`](../playbooks/research/p2-keyword-root.md#阶段-07--非英语市场开工卡目标市场非英语时必填)
阶段 0.7 的开工卡分别看量与 SERP，不能把同语言的多个地区合并成一个裁定。

**单语种裁定**：

| 情况 | 裁决 |
|---|---|
| 某语种流量大而竞争小 | **只做该语种的单语站，不做多语言。** 全部页面、TDK、`<html lang>`、内容都对准这一个语种 |
| 多个语种都有量 | 先做量最大且 KD 最低的那个单语站；其余记进 `.rankup/roadmap.md` 作为扩张候选 |
| 单语站已拿到流量（排名稳、有持续曝光） | 进入扩张期，此时才适用 [`experiences/webcafe-topics.md`](../experiences/webcafe-topics.md) 七「先做 2–3 个语言」 |

**为什么**：多语言是流量证明之后的扩张动作，不是起步配置。起步就做多语言，每个语种的内容都薄，
哪个都排不上；单语站把一个语种做厚，先证明这个词根能带流量，再复制到下一个语种。
`webcafe-topics.md` 七那条「先做 2–3 个语言」说的是**已验证的扩张期**，与本条不冲突。

### 2.2 意图类型 → 产品形态 → 变现方式

段 1 的网页、商店和原生使用证据共同决定形态：macOS、iOS、iPad、网站/SaaS 均可，唯独不做 Android App。离线/系统集成/触控绘制等任务优先评估原生；即时分享/跨平台协作可评估Web。按真实用户任务选择，不以低网页量强迫放弃App或改做网站：

| 意图类型（SERP 前十在排什么） | 产品形态 | 变现方式 | 路由 |
|---|---|---|---|
| 信息型（文章、问答、百科、对比） | 内容站 | 接广告（AdSense / Adsterra），后期联盟 | [`monetization.md`](../monetization.md) 广告一节 |
| 工具型（一次性完成一件事：转换、生成、计算、下载） | 在线工具页 / macOS、iOS、iPad App（商店或适用的直销渠道） | 单次付费、去水印/高清解锁、客户端买断 | [`monetization.md`](../monetization.md) Stripe / PayPal / 商店上架 |
| 持续使用型（每天/每周回来用：管理、追踪、协作） | SaaS / macOS、iOS、iPad App | 订阅或买断，按使用价值验证 | [`monetization.md`](../monetization.md) 订阅一节 |
| 混合（工具型意图但 SERP 上是内容页） | 工具页 + 内容页各一 | 工具收费，内容接广告 | 两节都读 |

**支付按分发方式接入**：Web直销走段3.4；App按商店和市场当前规则验证IAP/买断/订阅，macOS直销另记授权与支付。见 `monetization.md` 五，不强制所有App接Stripe+PayPal。

后续Web的shadcn、Cloudflare、SEO/URL检查只适用Web面。原生开发用对应平台工具与专项Skill（macOS可用build-macos-apps），App包/商店发布走 `monetization.md` 五；网页项不适用时记N/A与原因，不强建网站。

### 输入

- 通过段 1 门禁的机会或已有网站的明确变更目标。
- 用户旅程、内容需求、非功能要求、预算、合规和运营约束。
- 已有代码与基础设施（如有）。

### 必做动作

1. 按 2.1 选定语种与市场，落一条单语种裁定（做哪个语种、为什么不做多语言、扩张候选是谁）。
2. 按 2.2 从意图类型推出产品形态与变现方式，落 `.rankup/PROJECT.md`。
3. 定义产品范围、非目标、关键页面、用户路径和验收标准。
4. 设计 Monorepo 边界、TanStack Start SSR/API、数据模型、鉴权、支付、内容与分析方案。
5. 按真实需求选择 Cloudflare 资源，不为猜测中的未来需求预建复杂设施。
6. 区分 preview、staging、production 的资源、域名、数据和发布策略。**此时域名只是一个待定项**，写「待段 5 定稿」，不在本段选。
7. 定义数据迁移、失败恢复、可观测性与回滚路径。
8. 记录重要选项、依据、代价和被否决方案。

### 步骤 check

**每步做完就核，不要攒到闸门再一起补。** 闸门（[`checklists.md`](../checklists.md)）判的是「这个环节能不能算完」，下表判的是「这一步做对了没有」——闸门过不了，一定是下面某一行没过。

| 步 | 客观通过条件 | 证据 |
|---|---|---|
| 1 | 语种裁定落成一行：做哪个语种 + W1 的并排数据 + 不做多语言的理由 + 扩张候选；**没有起步就规划多语言路由** | `.rankup/decisions.md` |
| 2 | 意图类型 → 产品形态 → 变现方式三项按 2.2 对上，且意图类型引用的是段 1 的 SERP 核验记录，不是重新猜的 | `.rankup/PROJECT.md` |
| 3 | 范围、**非目标**、关键页面、用户路径、验收标准五项齐全。非目标不写，范围就会在实现时自己长大 | `.rankup/PROJECT.md` |
| 4 | Monorepo 边界、SSR/API 划分、数据模型、鉴权、支付、内容、分析各有一段设计，不是只有技术栈清单 | `.rankup/architecture.md` |
| 5 | 每个 Cloudflare 资源都能指出**当前**需求；**没有为猜测中的未来预建的设施** | `.rankup/architecture.md` |
| 6 | preview / staging / production 三套的资源、数据、发布策略逐项写明，没有共用同一份数据；域名一栏写的是「待段 5 定稿」 | `.rankup/infrastructure.md` |
| 7 | 迁移、失败恢复、可观测性、回滚四条路径各有一段，且回滚写到命令级 | `.rankup/architecture.md` |
| 8 | 重要选项连**被否决的方案与否决理由**一起记了——只记选中的，下次会重开同一场争论 | `.rankup/decisions.md` |

### 完成门禁

语种与市场已裁定为单语站（或写明为什么是例外）；产品形态与变现方式从意图类型推出并有记录；关键用户路径和验收标准可测试；每个选用的 Cloudflare 服务都有明确需求、binding、环境边界和失败处理；高风险数据、支付和发布动作均有迁移或回滚方案。
