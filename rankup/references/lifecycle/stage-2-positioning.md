### 硬规则（全文，含「为什么」；`SKILL.md` 只留摘要）

关键词与立项裁决只见 [`entry.md`](../playbooks/entry.md#选词判据只看两个)；本段写市场、产品形态与页面规划，不新增市场评分项。

### 2.1 第一目标是拿到流量，并选定语种

按段 1 的入口卡与两路结论选定市场和内容语言；跨市场测量方法只见 [`trends.md` W1](../trends.md#w1--小语种小国市场竞争力探测)。

**定位精确到 locale（语言-地区）**：同语言的不同国家分别引用 [P2 阶段 0.7 开工卡](../playbooks/research/p2-keyword-root.md#阶段-07--非英语市场开工卡目标市场非英语时必填)，不把多个地区合成一个裁定。

| 情况 | 规划落点 |
|---|---|
| 一个市场已有可做问法簇 | 起步默认单语站；页面、TDK、`<html lang>` 对准该市场的表达与任务 |
| 多个市场都有可做问法簇 | 引用各自入口卡，按可交付任务与现有执行约束确定先做哪个；其余记入 `.rankup/roadmap.md` |
| 单语站已拿到持续曝光与流量 | 再评估扩张市场的两路证据；[`webcafe-topics.md`](../experiences/webcafe-topics.md) 七的「先做 2–3 个语言」仅作已验证扩张期的经验参考 |

【经验】起步单语便于把已验证任务做完整；多语言是验证后的扩张动作。例外写清用户要求或现有产品约束与依据，不把单语偏好当市场否决。

### 2.2 意图类型 → 产品形态 → 变现方式

段 1 的网页、商店和原生使用证据共同决定形态：macOS、iOS、iPad、网站/SaaS 均可，唯独不做 Android App。离线/系统集成/触控绘制等任务优先评估原生；即时分享/跨平台协作可评估Web。按真实用户任务选择，不以低网页量强迫放弃App或改做网站：

| 意图类型（问法任务与 Google 卡） | 产品形态 | 变现方式 | 路由 |
|---|---|---|---|
| 信息型（文章、问答、百科、对比） | 内容站 | 接广告（AdSense / Adsterra），后期联盟 | [`monetization.md`](../monetization.md) 广告一节 |
| 工具型（一次性完成一件事：转换、生成、计算、下载） | 在线工具页 / macOS、iOS、iPad App（商店或适用的直销渠道） | 单次付费、去水印/高清解锁、客户端买断 | [`monetization.md`](../monetization.md) Stripe / PayPal / 商店上架 |
| 持续使用型（每天/每周回来用：管理、追踪、协作） | SaaS / macOS、iOS、iPad App | 订阅或买断，按使用价值验证 | [`monetization.md`](../monetization.md) 订阅一节 |
| 混合（工具型任务与内容解释并存） | 按 2.3 合并承接或拆页 | 工具收费，内容接广告 | 两节都读 |

**支付按分发方式接入**：Web直销走段3.4；App按商店和市场当前规则验证IAP/买断/订阅，macOS直销另记授权与支付。见 `monetization.md` 五，不强制所有App接Stripe+PayPal。

后续Web的shadcn、Cloudflare、SEO/URL检查只适用Web面。原生开发用对应平台工具与专项Skill（macOS可用build-macos-apps），App包/商店发布走 `monetization.md` 五；网页项不适用时记N/A与原因，不强建网站。

### 2.3 问法簇 → 页面 → FAQ/description与站点结构

本节是页面映射的唯一规则源；输入字段沿用 [`seo-geo.md` 三清单](../seo-geo.md#步骤-3推荐位竞争分析)，裁决沿用 [`entry.md`](../playbooks/entry.md#4--判读)，不在规划阶段重新采样或另设门禁。

| 规划动作 | 写法与依据 |
|---|---|
| 聚簇与合并 | 按用户任务、意图与约束归簇；同任务且同页面能完整满足的多条问法共一页，不按关键词字面差异批量拆页 |
| 拆页与页面类型 | 不同任务或需要独立能力/解释时拆页；首页说明产品核心任务，工具页完成操作，场景/比较/帮助内页承接对应需求；类型引用逐问法 Google 卡和真实能力 |
| 主词与辅助问法 | 每页登记一个用于表达和测量的目标短语，保留同簇辅助词与问法原话；一个主词不是只能承接一条问法 |
| 正文与 FAQ | 正文先完成核心任务；FAQ 承接该页相关的自然追问、限制与选择问题，答案据真实能力及已核实事实写；无对应问法不为凑数量造 FAQ |
| description | 用当地自然表达概括任务、可交付结果与适用限制；引用问法及本页事实，不复制整条问法或堆辅助词，不承诺尚未具备的能力 |
| 站点结构与优先序 | 首页 → 任务/分类 → 内页的路径对准用户任务，相关页面互链；优先完成有证据且当前能交付的任务，缺能力或缺证据的页面标待规划/待验证及下一步 |

在 `.rankup/keywords.md` 的 URL 对应项维护下表，长内容可放页面 Brief 并留指针；三清单的页面项引用该规划，不复制第二份。

| 页面/建议 URL与类型 | locale / 问法簇编号 | 核心任务与真实能力 | 主词 / 辅助词及问法编号 | SEO / GEO结论与入口卡、Google卡、样本/理由核实指针 | 正文结构 / FAQ问法及事实来源 | description草稿及问法/事实来源 | 相关页/导航入口 | 优先序、状态与缺项 |
|---|---|---|---|---|---|---|---|---|
| `<URL / 类型>` | `<市场 / 簇>` | `<任务 / 已有或需实现能力>` | `<目标短语 / 问法引用>` | `<路线 / 原始证据引用>` | `<承接位置 / 问法 / 核实来源>` | `<自然表达 / 来源>` | `<入口与互链>` | `<先后理由 / 状态 / 下一步>` |

页面 Brief 沿此表落实结构与 TDK；新增内页复用同市场、同任务的有效证据，仅补新问法或缺项。未覆盖的 FAQ/description 主张回到原始证据核实，不把规划草稿当推荐事实。

### 输入

- 段 1 移交的入口卡、两路结论与三清单，或已有网站的明确变更目标；裁决只见 [`entry.md`](../playbooks/entry.md#4--判读)，完成验收见 [`checklists.md` 段 2](../checklists.md#段-2--立项与定位)。
- 用户旅程、内容需求、非功能要求、预算、合规和运营约束。
- 已有代码与基础设施（如有）。

### 必做动作

1. 按 2.1 选定 locale，记录入口卡、起步语种、例外依据与扩张候选。
2. 按 2.2 从意图类型推出产品形态与变现方式，落 `.rankup/PROJECT.md`。
3. 按 2.3 落页面映射与站点结构，定义产品范围、非目标、用户路径和验收标准。
4. 设计 Monorepo 边界、TanStack Start SSR/API、数据模型、鉴权、支付、内容与分析方案。
5. 按真实需求选择 Cloudflare 资源，不为猜测中的未来需求预建复杂设施。
6. 区分 preview、staging、production 的资源、域名、数据和发布策略。**此时域名只是一个待定项**，写「待段 5 定稿」，不在本段选。
7. 定义数据迁移、失败恢复、可观测性与回滚路径。
8. 记录重要选项、依据、代价和被否决方案。

### 步骤 check

**每步做完就核，不要攒到闸门再一起补。** 闸门（[`checklists.md`](../checklists.md)）判的是「这个环节能不能算完」，下表判的是「这一步做对了没有」——闸门过不了，一定是下面某一行没过。

| 步 | 客观通过条件 | 证据 |
|---|---|---|
| 1 | locale、入口卡依据、起步语种或例外理由与扩张候选可回读 | `.rankup/decisions.md` |
| 2 | 意图类型 → 产品形态 → 变现方式三项按 2.2 对上，且意图类型引用的是段 1 的 SERP 核验记录，不是重新猜的 | `.rankup/PROJECT.md` |
| 3 | 范围、非目标、用户路径与验收标准齐全；页面映射按 2.3 可追溯 | `.rankup/PROJECT.md` + `.rankup/keywords.md` |
| 4 | Monorepo 边界、SSR/API 划分、数据模型、鉴权、支付、内容、分析各有一段设计，不是只有技术栈清单 | `.rankup/architecture.md` |
| 5 | 每个 Cloudflare 资源都能指出**当前**需求；**没有为猜测中的未来预建的设施** | `.rankup/architecture.md` |
| 6 | preview / staging / production 三套的资源、数据、发布策略逐项写明，没有共用同一份数据；域名一栏写的是「待段 5 定稿」 | `.rankup/infrastructure.md` |
| 7 | 迁移、失败恢复、可观测性、回滚四条路径各有一段，且回滚写到命令级 | `.rankup/architecture.md` |
| 8 | 重要选项连**被否决的方案与否决理由**一起记了——只记选中的，下次会重开同一场争论 | `.rankup/decisions.md` |

### 完成门禁

先核 [`checklists.md` 段 2 的用词实测闸门](../checklists.md#段-2--立项与定位)，通过后才交给段 3 建站。

语种与市场已裁定为单语站（或写明为什么是例外）；产品形态与变现方式从意图类型推出并有记录；关键用户路径和验收标准可测试；每个选用的 Cloudflare 服务都有明确需求、binding、环境边界和失败处理；高风险数据、支付和发布动作均有迁移或回滚方案。
